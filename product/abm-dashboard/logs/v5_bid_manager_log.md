## 1. 現状確認メモ

### 1.1 影響度ランキング（段階①）の現状

私は `product/abm-dashboard/static/index.html` を確認し、以下を把握した。

- `REVERSE_STAGE1_PARAMS` は 7 パラメータ固定:
  - `alpha`, `k1`, `budget_c0`, `budget_c1`, `gamma`, `difficulty_0`, `funds_0`
- 段階①は各パラメータにつき `75% / 100% / 125%` の 3 点を評価するため、総呼び出し回数は **7 × 3 = 21 回**
- `runReverseStage1()` では `sweepNTrials = Math.min(80, Math.max(1, basePayload.n_trials))`
  - したがって各点の試行回数上限は **80**
- 各点は **1回のみ** API 実行される
- 各点の `dominant_leader_pct` は `response.per_trial` から「独走勝ち組型に入った試行の割合」として算出される
- `summarizeQuadrantSweep(low, base, high)` は
  - `deltaLowPt = low - base`
  - `deltaHighPt = high - base`
  - `maxAbsDeltaPt`
  - 単調増加 / 単調減少 / 非単調
  だけを返しており、**標準誤差・信頼区間・有意性判定が存在しない**
- 段階①テーブルの表示列は現状:
  - パラメータ
  - 低/基準/高の独走勝ち組型%
  - 傾向
  - 最大変化幅(pt)
  - 参考: 基準の平均純利益
- 注意書きには「粗いランキング」「暫定値」とあるが、**どの差分がノイズで説明しうるかの見分けはUI上でできない**

### 1.2 v4 Architect ログからの確認事項

私は `product/abm-dashboard/logs/v4_architect_log.md` を確認し、特に以下を重視した。

- 同一設定でも **`n=150` で 2〜3pt 程度のブレ**が実測されている
- 共通乱数法によりブレは一部低減されるが、試行終了タイミング差による限界がある
- 現行の段階①はあくまで「局所3点スイープ」による粗い近似であり、遠方の非線形な相転移を保証しない

### 1.3 デザインの現状

私は `index.html` 冒頭のCSSも確認した。

- `:root` に `--color-*`, `--shadow-panel`, `--radius-*` などの既存トークン体系がある
- 全体は slate / blue 系の落ち着いたUI
- 主要コンポーネントは `panel`, `strategy-card`, `reverse-calc-card`, `sensitivity-table`, `button` 等のクラスで統一されている
- 現状は見やすいが、**専任デザイナーによるブランド定義・視覚ルールの確定プロセスは未実施**

## 3. Acceptance Criteria (AC)

## AC群A — 影響度ランキングの信頼性向上

### A-1. 呼び出し回数・試行回数の固定

- AC-A1.1: 段階①の総API呼び出し回数は現行どおり **21回** とし、増やさないこと
- AC-A1.2: 各点の `n_trials` は現行どおり `min(80, form.n_trials)` を維持し、上限80を変更しないこと
- AC-A1.3: 対象パラメータ集合（7個）と `75% / 100% / 125%` の3点スイープ構成は維持すること

### A-2. 解析的な不確実性評価の追加

- AC-A2.1: `dominant_leader_pct` について、各点の試行回数 `n` と比率 `p` から、**解析的な標準誤差または信頼区間**を算出すること
- AC-A2.2: 少なくとも **低vs基準、 高vs基準** の差分について、「観測差分がノイズで説明しにくいか」を示す判定材料を算出すること
- AC-A2.3: その判定は追加シミュレーションではなく、既存レスポンス (`per_trial` / 集計値) のみから求めること
- AC-A2.4: 判定ロジックの具体的手法（正規近似、Wilson系、共通乱数をどう扱うか、多重比較補正の扱い等）は Architect が確定する。ただし Bid Manager 観点では、**「差分の方向に統計的な裏付けがあるか」を利用者が読めること**を必須要件とする

### A-3. `summarizeQuadrantSweep()` 相当の判定強化

- AC-A3.1: 現在の単純な単調性判定だけでなく、**方向性の確からしさ**を返せるように集計仕様を拡張すること
- AC-A3.2: 方向ラベルは少なくとも以下のような3値以上を区別できること
  - 方向性あり（増加/減少）
  - 変化は観測されたが不確実性が大きい
  - 傾向不明瞭 / 判定保留
- AC-A3.3: `maxAbsDeltaPt` の大きさだけで順位付けして終わらず、**「差分が大きいが確信度は低い」ケースが読み取れる**こと

### A-4. 表示UIの要件

- AC-A4.1: 段階①の結果表に、**有意性または確信度を示す列 / ラベル / バッジ / 注記**を追加すること
- AC-A4.2: 各パラメータ行について、利用者が
  - 変化幅（pt）
  - 方向
  - その方向の信頼度
  を一目で区別できること
- AC-A4.3: 視覚表現は色だけに依存せず、文言・アイコン・バッジ等を併用して意味が伝わること
- AC-A4.4: 既存の「粗いランキング」「暫定値」注意書きを更新し、**解析的判定は追加するが、局所3点・最大80試行の粗い探索である点は依然として残る**ことを明記すること

### A-5. ランキングの解釈ルール

- AC-A5.1: 「有意でない / 不確実性が大きい」パラメータは、利用者に **“効かない” と誤認させず、“この設定の試行数では傾向不明瞭”** と解釈できる表現にすること
- AC-A5.2: 上位候補選定に段階①結果を使う場合、Architect は **不確実性ラベルを踏まえた並べ替え・選定ロジックの妥当性**を確認すること
- AC-A5.3: 実装後、少なくともノイズが小さい明瞭ケースと、2〜3pt級の微差ケースの双方で、表示が意図どおり分かれることを確認できること

## AC群B — デザイン確定（Brand Designer新設）

### B-1. ロール追加と責務分離

- AC-B1.1: 既存4ロールとは別に、**Brand Designer** を新規5番目ロールとして追加すること
- AC-B1.2: Brand Designer は、Architect の技術仕様策定と並行して、UIの視覚仕様を専任で確定すること
- AC-B1.3: Architect は構造・実装制約を整理し、Brand Designer は視覚ルールを決める、という責務分離を明確にすること

### B-2. Brand Designer が確定すべき仕様範囲

- AC-B2.1: Brand Designer は少なくとも以下を仕様化すること
  - 配色体系
  - タイポグラフィ体系
  - 余白 / 密度 / レイアウトリズム
  - パネル / テーブル / ボタン / バッジ / フォーム / カード等のコンポーネントスタイル
- AC-B2.2: 既存の slate / blue 系トークン体系に拘束されず、**白紙からのフルリデザイン**を許可すること
- AC-B2.3: ただし Brand Designer は「何を表示する画面か」「どのパネルがどこにあるか」という情報構造を理解したうえで、視覚面を再設計すること

### B-3. 維持すべき体験

- AC-B3.1: 以下の主要機能・情報構造は維持すること
  - シミュレーション条件入力
  - サマリー表示
  - 感度分析
  - 段階① 影響度ランキング
  - 段階② 組み合わせ探索
  - 四象限散布図
- AC-B3.2: 機能の存在順序や基本的な操作フローを大きく崩さず、**学習コストを増やさない刷新**であること
- AC-B3.3: テーブル・注記・状態表示・ボタンの優先度が視覚的に整理され、特に段階①/②の関係が現状以上に理解しやすくなること

### B-4. 品質条件

- AC-B4.1: 新デザインは、既存機能を隠したり判別困難にしたりせず、可読性を改善または少なくとも維持すること
- AC-B4.2: 色・余白・強調ルールは一貫しており、「主要アクション」「注意」「参考情報」「未確定/不明瞭」の区別が視覚的に伝わること
- AC-B4.3: アクセシビリティ（コントラスト、情報の色依存回避、フォーカス視認性等）を損なわないこと
- AC-B4.4: Brand Designer は最終的に、実装者が `index.html` のCSS/HTMLへ落とし込める粒度で、トークン方針とコンポーネント方針を言語化すること

## 4. リスク・懸念点

### 4.1 ランキング信頼性向上のリスク

- `n <= 80` の二項比率では、差分が小さいケースで判定がかなり粗くなる可能性が高い
- `p` が 0% や 100% 近傍に寄ると、単純な正規近似の精度が悪化しうる
- 現状は共通乱数法を使っているため、独立標本前提の単純比較は厳密にはズレる可能性がある
- 7パラメータ × 2比較（低vs基準、高vs基準）という多重比較的な状況なので、見かけの差を過信するリスクがある
- したがって私は、「厳密な統計的真実を断言するUI」ではなく、**“傾向の確からしさを補助表示するUI”** として扱うべきだと判断する

### 4.2 デザイン刷新のリスク

- フルリデザインの自由度が高いぶん、情報構造や優先順位を壊す危険がある
- 表現を大胆に変えすぎると、段階①/②や補助注記の意味が逆に分かりにくくなる可能性がある
- 表やバッジが増えるため、視覚ノイズが増えるリスクがある
- そのため Brand Designer には、**美しさだけでなく、分析UIとしての可読性・比較容易性・状態認識性**を成果物要件として明示すべき
