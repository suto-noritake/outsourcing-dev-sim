AC3: 逆算（感度/探索）機能

- AC3.4: 組合せ探索: 上位K(=3)の影響パラメータでグリッドサーチ（各パラメータ3値→3^K組合せ）を実行し、上位M(=5)候補を精密検証して推奨設定を提示。
- AC3.5: 逆算は各戦略（conservative/cost_optimal/adaptive）ごとに実行可能で、UIで戦略選択毎にボタンを設置。

AC4: UI表記と注意書き

## 2. 実装方針（ドラフト）

2.1 スライダー min/max/step の提案（根拠: app.py の pydantic Field 制約 と outsourcing_sim/params.py のデフォルト）
- alpha: min=0.01, max=2.0, step=0.01 (app: gt>0, le=2.0, default=0.6)
- beta: min=0.01, max=20.0, step=0.01 (gt>0, le=20.0, default=3.0)
- lam: min=0.0, max=1.0, step=0.01 (ge=0.0, le=1.0, default=0.7)
- k1: min=0.01, max=50.0, step=0.01 (gt>0, no upper bound in pydantic → choose 50 as practical cap)
- cost_curve_exponent: min=0.5, max=5.0, step=0.1 (ge=0.5, le=5.0)
- sigma_noise: min=0.0, max=2.0, step=0.01 (ge=0.0, le=2.0)
- gamma: min=0.0, max=2.0, step=0.01 (ge=0.0, le=2.0)
- partial_pay: min=0.0, max=1.0, step=0.01 (ge=0.0, le=1.0)
- r_min: min=0.0, max=1.0, step=0.01 (ge=0.0, le=1.0)
- max_consecutive_failures: min=1, max=50, step=1 (ge=1, le=50)
- difficulty_0: min=0.01, max=20.0, step=0.01 (gt>0, difficulty_cap default 20)
- funds_0: min=1.0, max=10000.0, step=1.0 (gt>0, default=100.0 — cap chosen pragmatically)
- difficulty_cap: min=1.0, max=100.0, step=0.1 (gt>0)
- budget_c0: min=0.0, max=100.0, step=0.5 (ge=0)
- budget_c1: min=0.0, max=500.0, step=0.5 (ge=0)
- max_rounds: min=1, max=1000, step=1 (ge=1, le=1000)
- n_trials (control): min=1, max=500, step=1 (api limit)
- base_seed: integer slider or number input: min=0, max=1000000, step=1
- strategy: select remains unchanged (no slider)

根拠: pydantic Field の gt/ge/le を尊重。上限/下限が未定義のもの（k1, funds_0, budget系等）は実務上の有意な範囲を選定し、Architect に最終確認を求める。

2.2 リアルタイム更新のデバウンスと n_trials 設定
- "ドラッグ中" の概念は `input` イベントで捕捉。実装: oninput イベントで local preview を発火するが、サーバ呼び出しはデバウンス:
  - プレビュー呼出し: debounced 200ms（入力継続時は間引き）
  - 精密呼出し: onmouseup / ontouchend => 直ちに精密呼出し（n_trials = form.n_trials）
- プレビュー用 n_trials: 20（軽量、応答性重視）。理由: 実行時間観測値から判断して十分速い一方で乱数ノイズが極端に支配的にならない最低限の妥当値。
- プレビュー・精密レスポンスは UI 上で分かりやすく差分表示: メトリクスカード上に小さなラベル "プレビュー(n=20)" / "精密(n=100)" を表示し、最新の種別を強調する。

2.3 逆算（感度 → 組合せ探索 → 推奨設定）アルゴリズム案
全体方針: 探索はフロントエンドで複数回 `/api/simulate` を呼び、結果集計・ランキング・最終検証は精密 n_trials でサーバ呼出しして提示する。

ステップA: 単体スイープ（感度推定）
- 対象パラメータ: 初期ドラフト候補として [alpha, k1, budget_c0, budget_c1, gamma, difficulty_0, funds_0]
- 各 param について 3点: low=base*0.75, base, high=base*1.25（適宜クランプ、例: sigma_noise <=2.0, difficulty_cap >= difficulty_0 など）
- 呼び出し: 各点についてプレビュー向け n = min(150, form.n_trials) を使う（v3方針）。共通 base_seed を利用して乱数ノイズを部分低減。
- 呼び出し回数: P parameters × 3 calls（Pは対象パラメータ数）
- 結果: 各点の mean_net_profit を取得、summarizeSweep ロジックで %変化・単調性を決定。ランキングで各パラメータの "感度"（maxAbsDeltaPct）をソート。

ステップB: 組合せグリッドサーチ（推奨設定生成）
- 上位 K=3 パラメータを選定（感度が大きい順）。各パラメータで 3 値（0.75/1.0/1.25）→ 3^K 組合せ（最大27通り）。
- まずプレビューn（例: 20）で全組合せを評価し、平均純利益で上位 M=5 を選ぶ。
- 次に上位Mを精密 n_trials（フォームのn_trials）で再評価して最終ランク付けし、最上位1-3を「おすすめ設定」として提示。
- 呼び出し回数見積もり: プレビュー段階で up to 27 calls; 精密検証で up to 5 calls → 合計最大32追加呼出し（戦略1種あたり）。
- ガードレール: UI上で概算所要時間を表示し、ユーザーの明示的承認（OK）を得てから実行する。自動実行は禁止。

注意: 上の呼び出し回数は戦略1つあたりの見積り。ユーザーが全3戦略で実行する意図がある場合は各戦略で同様のコストがかかる（ただし感度チェックの軽量版は最大6回に制限する既存v3のルールを踏襲可能）。組合せグリッドはユーザーが明示的に起動した場合のみ実行すべきであり、オプトインにする。

2.4 UIのレイアウト案（統合）
- 既存のフォームレイアウトを保ちつつ、数値入力を左右にスライダーを配置（下段に小数値の直接入力を残す）。スライダーは横幅100%でラベル上に現在値表示。
- プレビューと精密のステータス: Summaryパネル上部に小さなバッジを追加（色分け: 青=プレビュー, 濃青=精密）。
- 逆算パネル: 感度チェックの下に「逆算（自動推奨）」セクションを追加。段階的UI:
  1) 単体感度ボタン(既存を拡張) → 実行結果テーブル（param / low/base/high / %変化 / 傾向）
  2) 組合せ探索ボタン（"候補設定を探索") → 実行前に概算所要時間ダイアログ → 実行 → 結果カード（上位候補＋精密検証ボタン）
- 四象限凡例/感度チェックパネルは現状と同居。比較モード時は quadrant-legend に形状注釈が表示される。

## 3. フィージビリティ評価（バックエンド変更の必要性）

結論: 基本的にはバックエンドの変更は不要（/api/simulate を繰り返し呼ぶアプローチで実現可能）。理由:
- app.py の SimulateRequest は n_trials, base_seed, params を受け取れるため、フロントから複数回呼び分けるだけでスイープ・グリッド検索が可能。
- simulate のレスポンスに per_trial / aggregates / plot_data が含まれており、フロントで必要な集計（四象限分布, 傾向コメント, 感度集計）は追加通信なしで算出できる。

ただし検討事項・潜在的課題:
- パフォーマンス: 大量の追加呼出し（組合せ探索の最大ケース）でサーバCPU負荷や応答遅延が発生する。運用的な制約（同時実行数上限、リクエストレート制限、タイムアウト）をArchitect/Infraと協議のうえガードを追加する可能性がある。
- 同期性: 同じ base_seed を使ったcommon-randomness を前提にするため、フロントで同じ base_seed を使って繰り返し呼ぶ実装でOK。ただし simulate の内部が分岐で乱数消費列が変わるため完全な差分消去は保証されない点を注記する。
- 新機能（組合せグリッド探索）が多数の呼出しを行うため、場合によってはバックエンドに簡易ジョブキュー/バッチAPIを追加して非同期で実行→完了通知で結果を取得する方が望ましい。これはGo後の改善案として推奨。

## 4. Go / No-Go 判断

判定: Go（実装可能）
理由:
- すべての機能はフロントエンドから既存 `/api/simulate` を利用して実現可能で、v3 Architect の指摘（Pearson r の不採用・ジッター不採用等）を反映すれば統計的/可視化上のリスクは低減できる。
- ただし組合せグリッド探索や大規模の連続呼出しに対するパフォーマンス懸念があるため、実装時にUIでのオプトインと事前見積り・実行制御を必須にする。将来的にジョブキュー化が望ましい。

## 5. 次工程（Architect）への申し送り事項（検証リスト）

私は以下点について最終的にソースコードでの確認・判断をArchitectに依頼します（優先順位順）:

1) 逆算対象パラメータの最終確定: 特に alpha と funds_0 のレンジがモデル挙動に与える非線形性が大きいため、pydantic の制約とSimParamsのデフォルトを基に実コードで sensivity を検証しレンジを確定してください。
2) k1 の実効上限: app.py に上限がないためフロントで設定した最大値(例 50)が妥当かどうか。内部で cost に直線的に乗るため過大な上限は過負荷を招く可能性あり。
3) グリッド探索の最大呼出し数に関する運用制約: 同時実行リクエスト数、タイムアウト、APIスロットリングの有無をInfraと確認してください。必要なら API 側で簡易ジョブ受付（非同期）を検討。
4) sigma_noise の挙動説明: model.py の実装（期待値が exp(sigma^2/2) によりコスト期待値を上げる）をUI表記に反映する文言を最終確認してください（現状UIは「ブレ」と説明しているが「期待値変化」も明記すべき）。
5) common random numbers の限界: simulate の実装（run_many/run_game の内部乱数消費の分岐）により完全な対応は取れないため、表現を「ばらつきの一部を低減する工夫」と限定することを確認してください。
6) 大量連続呼出し時の測定: 組合せ探索の想定最大ケース（例: 27 プレビュー + 5 精密）を実際にローカル/ステージで負荷試験し、平均応答時間とサーバ負荷の実測値を報告してほしい。
