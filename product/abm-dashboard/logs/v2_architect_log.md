## 1. Bid Manager 付録の事実誤認の指摘（修正前 → 何が違うか）

以下は Bid Manager 案の「パラメータ日本語説明」のうち、ソースコード上の実際の挙動と食い違っていた、
または誤解を招く記述だったものである。

| パラメータ | Bid Manager案の問題点 | 実際の挙動（根拠） |
|---|---|---|
| `beta` | 「競争強度。市場での競争圧力。大きいほど競争が激しく、成功確率が下がります」→ **誤り**。競争の概念はモデルに存在しない。 | `model.py: success_probability` = `sigmoid(beta*(Capability-Difficulty))`。betaは**シグモイドの急峻さ**。大きいほど「技術力が難易度を上回れば成功・下回れば失敗」という白黒がハッキリつくだけで、技術力が難易度を上回っている限り成功率自体は下がらない。 |
| `k1` | 「基礎能力係数。値が大きいほど能力が増しやすい」→ **誤り**。能力(capability)には一切関与しない。 | `model.py: credit_cost` = `k1 * cost_mult(tier) * n * D * noise`。`capability()`関数はalphaのみを使い、k1は登場しない。k1は純粋な**コスト側**の基準倍率。 |
| `gamma` | 「成長率係数。能力成長に関わる。大きいほど能力が上がりやすい」→ **誤り**。B社(受託側)の能力とは無関係。 | `simulate.py: run_game` 内、成功時に `client.difficulty = min(difficulty*(1+gamma), cap)` を実行しているのは **クライアントA(発注側)**。gammaは「A社が成功のたびに要求難易度をどれだけ吊り上げるか」＝クライアントの強欲さ・エスカレーション率であり、B社の成長速度ではない。 |
| `r_min` | 「最低報酬率。0〜1の報酬比率」→ **誤り**。金額・支払比率とは無関係。 | `simulate.py`: `terminated = ... or client.reputation < params.r_min` → **信頼度(評判)の下限**。これを下回るとAが契約を打ち切る、契約継続の可否を決める閾値であり、報酬額(partial_pay等)とは別軸。 |
| `lam` | 「成功感度(λ)。成功確率に影響する感度パラメータ」→ **誤り**。成功確率(`success_probability`)の計算には登場しない。 | `simulate.py`: `client.reputation = lam*reputation + (1-lam)*success` → **評判の指数移動平均(EMA)の平滑化係数**。信頼度が「直近の結果」と「過去の実績」のどちらを重視して更新されるかを決めるだけで、成功・失敗の判定式そのものには影響しない。 |
| `budget_c0` / `budget_c1` | 「コスト計算に使う定数（初期コスト/増分コストに関わる係数）」→ **誤り（Bid Manager案には無かったが私が発見した追加の誤り）**。B社側のコスト(`credit_cost`)には一切使われない。 | `simulate.py: _budget_for` = `c0 + c1*difficulty*(0.5+0.5*reputation)` は **クライアントAがB社に支払う契約予算(報酬)** の計算式。B社の支出(コスト)は `k1`/`cost_curve_exponent` 側の完全に別の式で決まる。「コスト計算」という表現は発注側の支払い額を受託側の費用と混同させる致命的な誤解を生む。 |

上記に加え、以下は「誤りではないが不正確・説明不足」で AC2.2 の「業務向けの平易な日本語＋期待される効果」
の水準を満たさないため、私の判断で書き直した：
`alpha`（方向性は合っていたが「影響減衰率」という命名が誤解を招く）、`cost_curve_exponent`（方向は正しいが
「何が」高くなるのか＝上位モデルのコストであることが欠落）、`sigma_noise`（コスト/工数のブレであり成功判定
とは無関係、という限定が欠落）、`partial_pay`（「失敗時のみ」支払われるという条件が欠落しており、常に部分
支払いされると誤読されうる）、`max_consecutive_failures`（「超えると」ではなく「到達すると(>=)」が正確）、
`strategy`（選択肢名の羅列のみで、各戦略が実際に何をするかの説明が皆無だったため新規に記述）。

四象限ラベル（dominant_leader 等）の意味・示唆については、`docs/DESIGN.md` と突き合わせた結果、
Bid Manager案は**方向性としては正しかった**（軸の高低の組み合わせと象限名の対応も一致）。ただし
「技術優位度(capability_margin)」「資金体力(funding_runway)」という軸の定義そのものの明記が付録に無かった
ため、§3 で軸定義を明示した完全版を提示する。

| # | パラメータ(API名/据置) | 日本語タイトル | 説明文（そのままUIに使用可） |
|---|---|---|---|
| 1 | `alpha` | エージェント人数投入の効き目 | 同じ案件に投入する人数を増やしたとき、技術力がどれだけ伸びるかを左右します。値が1に近いほど人数を増やした分だけ素直に技術力が伸び、0に近いほど人数を増やしても頭打ちになりやすくなります（3人目・4人目の追加効果が薄い）。 |
| 2 | `beta` | 成功・失敗の白黒のつきやすさ | 技術力が案件の難易度を上回っているかどうかで、成功・失敗がどれくらいハッキリ決まるかを表します。値が大きいほど「技術力が難易度を上回っていればほぼ確実に成功、下回っていればほぼ確実に失敗」という結果になり、僅差の逆転が起きにくくなります。値を上げても成功率そのものが下がるわけではありません。 |
| 3 | `lam` | 信頼度（評判）の変わりやすさ | クライアントがB社に持つ信頼度を、直近の成功/失敗とこれまでの実績のどちらを重視して更新するかを表します。値が大きいほど信頼度はゆっくりとしか動かず（1回の失敗で急落しない代わり挽回にも時間がかかる）、値が小さいほど直近の結果に敏感に上下します。 |
| 4 | `k1` | コストの基準倍率 | 案件をこなすたびにかかる費用全体の水準を決める基礎係数です。技術力には影響せず、純粋に「同じ仕事にいくらかかるか」だけを底上げします。値が大きいほど同じ案件でもコストが高くつき、資金の減りが早くなります。 |
| 5 | `cost_curve_exponent` | 高性能モデルの割高さ | より高性能なモデル（Low→Mid→High→Frontier）を使うほど、コストがどれだけ急激に高くなるかを表す指数です。値が大きいほど「高性能ほど性能の伸び以上にコストが跳ね上がる」傾向が強まり、値が小さいほど高性能モデルでも比較的割安に使えます。 |
| 6 | `sigma_noise` | コスト・工数の見積もりのブレ | 毎ラウンドのコストや所要時間について、見積もりからどれだけ実績がブレるかを表します。値が大きいほど、同じ条件でも実際の費用・時間が予想より大きく上下しやすくなります。成功・失敗の判定そのものには影響しません。 |
| 7 | `gamma` | クライアントの要求エスカレーション率 | B社が案件に成功するたびに、クライアントが「次はもっと難しい仕事を」と要求難易度をどれだけ引き上げてくるかを表します。値が大きいほど成功のたびに難易度が急激に上がり、やがて技術力が追いつかなくなるリスクが高まります。B社自身の成長速度ではなく、クライアント側の「欲張り度」を表す値です。 |
| 8 | `partial_pay` | 失敗時の補填払い率 | 案件が**失敗に終わった場合に限り**、クライアントが契約予算の何割かを支払ってくれるかを表す割合（0〜1）です。0なら失敗した回の支払いは一切なく、1に近いほど失敗しても収入があるため資金への打撃が和らぎます。 |
| 9 | `r_min` | 契約打ち切りの信頼度ライン | クライアントが持つB社への信頼度（0〜1）がこの値を下回ると、クライアントは即座に契約を打ち切ります。値が大きいほど少しの信頼低下でも契約解除されやすく（基準が厳しい）、値が小さいほど信頼が多少下がっても契約が続きやすくなります（基準が緩い）。支払われる報酬額とは無関係です。 |
| 10 | `max_consecutive_failures` | 連続失敗の我慢の限度 | 案件に何回連続で失敗すると、クライアントが見切りをつけて契約を打ち切るかを表す回数です。値が大きいほど連続失敗にも猶予がありますが、値が小さいと少しのつまずきですぐ契約解除につながります。 |
| 11 | `difficulty_0` | 開始時点の案件の難易度 | シミュレーション開始時点で発注される案件の難易度です。序盤の技術力とのバランスが、最初の成功しやすさを左右します。 |
| 12 | `funds_0` | 開始時点の手持ち資金 | B社が事業を始める時点で持っている運転資金です（目安：中規模案件およそ10件分に相当）。この資金がなくなると倒産としてシミュレーションが終了します。 |
| 13 | `difficulty_cap` | 難易度の上限 | クライアントの要求エスカレーション（gamma）によって難易度が際限なく上がり続けないよう設ける上限値です。難易度はこの値を超えて上がりません。 |
| 14 | `budget_c0` | 契約予算の基本額 | クライアントがB社に支払う契約予算（報酬）のうち、案件の難易度に関係なく常に上乗せされる固定部分の金額です。値が大きいほど、簡単な案件でも一定額の報酬が保証されます。 |
| 15 | `budget_c1` | 難易度連動の予算係数 | 契約予算（報酬）のうち、案件の難易度とB社の評判に応じて増減する部分の大きさを決める係数です。値が大きいほど、難しい案件・評判が良い状態であるほど報酬が大きく積み増されます（評判が低いと上乗せ分は最大でも半分程度に割り引かれます）。 |
| 16 | `max_rounds` | 1回のシミュレーションの最大ラウンド数 | 倒産も契約打ち切りもせずに生き残れた場合の、最大継続ラウンド数です。この回数に達して終了した場合は「生き残り切った」という扱いで、悪い結果ではありません。 |
| 17 | `strategy` | B社の投資方針 | B社が毎ラウンド、どの性能のモデルを何人分投入するかを決める行動方針です。<br>・**conservative（保守的）**: 手持ち資金の半分を上限に、その範囲で最も技術力の高い組み合わせを選び、成功を最優先します。コストは度外視気味です。<br>・**cost_optimal（コスト最適）**: 成功確率がおよそ6割に達する範囲で最も安く済む組み合わせを選び、資金温存を優先します。<br>・**adaptive（適応型）**: 資金残量や直近の成績を見て方針を切り替えます。資金が残りわずかなら延命重視で安く済ませ、直近の成績が悪ければ立て直しのため思い切って投資し、順調なときはコストを抑えて手堅く稼ぎます。 |
| 18 | `n_trials` | 試行回数 | 同じ設定で「運（乱数）」だけを変えて何回シミュレーションを繰り返すか（1〜500）です。回数を増やすほど、成功率などの平均値の信頼性が上がります。 |
| 19 | `base_seed` | 乱数の開始番号 | シミュレーションの「運」を決める乱数の出発点となる整数値です。同じbase_seedと設定であれば、何度実行しても全く同じ結果が再現されます（比較実験の再現性確保用）。 |

## 3. 四象限ラベルの説明（軸定義を含む完全版）

**軸定義（必ず画面上のどこかに常設表示すること。AC3.2の前提として必須）**

- **X軸＝技術優位度（`capability_margin`）** = 技術力 − 案件の難易度。今受けている案件の難しさに対して、
  技術力がどれだけ上回っている（プラス）か下回っている（マイナス）かを表す。
- **Y軸＝資金体力（`funding_runway`）** = 資金残高 ÷ 直近の資金消費ペース（平均バーンレート）。今のペースで
  資金を使い続けた場合、あと何ラウンド持ちこたえられるかという「資金の残り時間」の目安。

| API上のenum値（変更不可） | 日本語ラベル | 状態の意味（1行） | ビジネス上の示唆 |
|---|---|---|---|
| `dominant_leader` | ①独走勝ち組型 | 技術優位度・資金体力ともに高い状態。案件が難化しても勝ち続けられる、最も理想的なポジション。 | 攻めの投資・案件拡大を検討してよい局面。 |
| `cash_starved_specialist` | ②宝の持ち腐れ／燃え尽き型 | 技術力は難易度を上回っているのに、資金体力が乏しい状態。技術はあるのに運転資金が続かず倒産リスクが高い。多くの受託会社がスタート地点として陥りやすい象限。 | 技術投資の拡大より先に、資金繰り（前受金交渉・部分払い改善など）を優先すべき局面。 |
| `deep_pockets_shallow_skills` | ③物量型／時間稼ぎ型 | 技術力は難易度に届いていないが、資金体力はある状態。リトライや低ティアモデルの大量投入で当面は延命できるが、失敗が続けば評判が悪化し④へ転落しやすい。 | 延命している間に技術力（モデルの質・体制）への根本的なてこ入れが必要な局面。 |
| `exit_candidate` | ④淘汰予備軍型 | 技術優位度・資金体力ともに低い状態。挽回の打ち手が乏しく、早期に契約打ち切りや倒産に至りやすい。 | 早期撤退・契約整理の検討、あるいは抜本的な立て直し投資の是非を判断すべき局面。 |

（参考・実装者向け情報: `model.quadrant()` は `funding_runway >= 5.0`（既定の`runway_threshold`、
SimParamsの調整可能項目ではない固定値）を「資金体力：潤沢」の閾値としている。UIで「潤沢/乏しい」の
数値基準を示したい場合はこの5ラウンドという値を注記してよいが、AC2.1の19項目には含まれないため
入力フォームに項目を追加する必要はない。）

## 4. 日本語ローカライズ方針（AC1）

**方針の原則**: 表示層（DOM文字列・ラベル・凡例・ツールチップ・エラーメッセージ）は全面的に日本語化する。
一方で `POST /api/simulate` のリクエスト/レスポンスJSON（`strategy: "adaptive"`,
`final_quadrant: "dominant_leader"` 等のenum値）は**英語のまま変更しない**。QAのv1回帰テスト
（`tests/test_api.py`）が英語enum値に依存しているため、バックエンド契約を壊すと既存テストが失敗する。
→ **表示専用の日英マッピング辞書（JS内定数）を新設し、DOM描画時にのみ変換する。fetchのpayload/レスポンス
解析には一切影響させない。**

### 4.1 翻訳が必要な文字列の一覧（index.html 内、現状把握済み）

- `<html lang="en">` → `lang="ja"`
- `<title>ABM Dashboard</title>` → 日本語タイトルへ
- 見出し: `ABM Simulation Dashboard`, `Parameters`, `Summary`,
  `Quadrant Scatter (capability_margin vs funding_runway)`, `Survival Rounds Histogram`
- 各入力ラベル19個（現状は`alpha`等の生のAPI名がそのままラベル文字列になっている）
  → §2の「日本語タイトル」に置換し、生のAPI名は `<small>` 等でサブラベルとして併記可（QAが
  パラメータ名とAPIフィールドの対応を確認しやすくするため、完全に隠さないことを推奨）。
- ボタン: `Baseline` → 「初期値に戻す」, `Run Simulation` → 「シミュレーション実行」,
  `Compare 3 strategies` → 「3戦略を比較」
- 補足文: `Compare mode ignores the strategy selector and runs conservative/cost_optimal/adaptive.`
  → 「比較モードでは戦略の選択は無視され、保守的・コスト最適・適応型の3戦略をまとめて実行します。」
- エラー表示: `Request failed: ${err}` → 「リクエストに失敗しました: ${err}」（`err`自体は技術的な
  英語メッセージのままでよいが、接頭辞は日本語化する）
- サマリーカード内: `success_rate`, `bankruptcy_rate`, `mean_survival_rounds`, `mean_net_profit`
  という生のキー名表示 → §5の指標名＋一行説明に置換
- サマリーカードの見出し `<h3>${strategy}</h3>`（`conservative`等の生enum値）
  → 表示専用マッピングで「保守的 (conservative)」のように**日本語＋括弧書きでenum併記**する
  （QAがenum値との対応を目視確認できるようにするため。データ属性は`data-strategy="conservative"`
  のまま保持）。
- 散布図/ヒストグラムの凡例ラベル（`strategy`名）、ポイント色分けの凡例（`quadrant`名）
  → 同様に日本語＋英語enum併記のマッピングを適用（Chart.jsの`label`フィールドに日本語文字列を
  渡してよい。データ自体のx/y/quadrant値は変更しない）。
- Chart軸タイトル: `capability_margin` → 「技術優位度」, `funding_runway` → 「資金体力」,
  `survival_rounds bin` → 「生存ラウンド数（区間）」, `count` → 「件数」
- README（AC1.2対象、本タスクでは編集しないが仕様として明記）: 「Setup」「API」「Preset buttons」
  「Tests」セクションのうち、**エンドユーザー向けの「起動手順」「使い方」部分のみ日本語化**。
  PowerShellコマンド自体・APIのcurl/PowerShell例はそのまま（開発者/QA向けのため英語のままでよい）。

## 6. チャートの引き伸ばし／歪み修正（AC5）— 原因診断と確定方針

**原因の特定**: 現状の `static/index.html` では、

1. `canvas { max-height: 400px; }` のみが指定されており、**canvasの直接の親要素
   （`.panel`）には明示的な高さ指定も `position: relative` も無い**。
2. `.panel` はブロック要素で、内容量（canvasの実サイズ）に応じて高さが決まる。Chart.jsの
   `responsive: true` はデフォルトで `maintainAspectRatio: true`（初期比率2:1）と併用されるため、
   親のサイズが定まらない状態でChart.jsが「親の幅を見てcanvasの高さを比率で決める→その高さが
   親の高さに影響する→Chart.jsが再度リサイズを検知する」という**循環的な参照**が起きやすい。
   これがChart.jsで広く知られる「グラフが際限なく伸びる／歪む」典型的な原因である
   （Chart.js公式ドキュメントが明示的に警告している「responsiveなcanvasは、サイズが確定した
   相対配置の親コンテナに入れる必要がある」というパターンに反している）。
3. `.grid` クラス（CSS Grid, `auto-fit, minmax(180px, 1fr)`）はフォーム入力欄用であり、チャートの
   `.panel` には使われていないが、ウィンドウ幅変化のたびに`.panel`自体の幅は変わるため、
   `maintainAspectRatio:true` のままだと**高さも連動して変わり続け**、ユーザーの目には「開くたびに
   縦横比が違う」「引き伸ばされる」ように映る。

**Bid Manager案（`maintainAspectRatio: true` を有効にし、CSSでmax-width/max-heightを設定）は不採用と
する。** 理由: `maintainAspectRatio:true` は「固定サイズが決まっていない親」の中では上記の循環参照
問題を解決しない。比率は保てても、コンテナ自体の実寸が不定なままなので歪み・伸縮の再発を防げない。
根本原因は「比率」ではなく「**親コンテナの寸法が確定していないこと**」にあるため、次の方式を確定仕様とする。

**確定方針: `maintainAspectRatio: false` ＋ 高さ固定のラッパーdiv。**

- 各 `<canvas>` を `position: relative; height: 400px; width: 100%;` を持つ
  `<div class="chart-container">` で包む。
  ```html
  <div class="chart-container">
    <canvas id="scatter-chart"></canvas>
  </div>
  ```
  ```css
  .chart-container { position: relative; height: 400px; width: 100%; }
  .chart-container canvas { max-height: none; } /* 旧 canvas{max-height:400px} ルールは撤去 */
  ```
- Chart.js初期化オプションで両チャートとも `options.maintainAspectRatio: false` を明示する
  （`responsive: true` はそのまま維持。widthはコンテナに追従、heightは常に400pxで固定）。
- モバイル（幅<=480px）では `.chart-container` の高さをメディアクエリで `height: 280px` 程度に
  縮小し、デスクトップ（幅>=1024px）は400pxを維持する2段階のブレークポイントを設ける
  （Bid ManagerのAC5.2「モバイル/デスクトップの2種確認」はこの固定高さの出し分けで満たす）。

この方式なら、幅が変化しても高さは常にCSSで確定した値に固定され、Chart.jsは「確定した箱を埋める」
だけでよく、循環参照も、ウィンドウリサイズのたびに縦横比が変わる現象も発生しない。これはChart.js公式が
推奨する標準的なレスポンシブ対応パターンである。

## 7. Windows用ワンクリック起動ランチャー設計（AC4）

**client要望「ダブルクリックして、それだけで動く」を踏まえた結論**: 表向きにユーザーがダブルクリックする
ファイルは **`launch_dashboard.vbs`**（コンソールウィンドウ非表示）とする。実体のロジックは
**`launch_dashboard.bat`** に実装し、`.vbs` はそれを非表示ウィンドウで起動するだけの薄いラッパーとする。

**理由（ADR形式で明記）**:
- 単純な`.bat`単体（可視コンソール）は実装・デバッグは容易だが、実行のたびに黒いコンソール窓が
  一瞬〜数秒開いてしまい、クライアントが明示的に嫌がった「起動が面倒」「分かりにくい」という体験を
  再生産する。今回は非技術者の業務担当者が使うダッシュボードであり、"それだけで動く"という要求に
  対しては窓が見えること自体がノイズになる。
- 一方で`.bat`を完全に廃止し全ロジックを`.vbs`に書くと、ロジックが複雑化した際のデバッグ・保守が
  困難になる（VBScriptは分岐・文字列処理が冗長）。
- そこで **ロジック本体は`.bat`（デバッグ・保守用に単体でも実行可能）、ユーザーの入口は`.vbs`
  （`.bat`を非表示で起動するだけ）** という2ファイル構成が両立解とする。サポート担当者が問題を調査する
  際は`launch_dashboard.bat`を直接ダブルクリックすればコンソール出力を見ながら原因究明できる。

### 7.1 `launch_dashboard.bat` の仕様

1. `cd /d "%~dp0"` でスクリプト自身の場所（`product\abm-dashboard\`）に移動する。
2. venvのpython実行ファイルを **`%~dp0`からの相対パス**で特定する:
   `set "VENV_PY=%~dp0..\..\.venv\Scripts\python.exe"`
   （絶対パス `C:\Users\4096361\...` は**ハードコードしない**。README記載の`..\..\.venv`という
   構成をそのまま踏襲し、リポジトリをどこにcloneしても動くようにする。）
3. `if not exist "%VENV_PY%"` の場合: 日本語のエラーメッセージを表示して終了する（下記7.3参照）。
   メッセージ例:「仮想環境(.venv)が見つかりません。リポジトリ直下で
   `python -m venv .venv` の後、`README.md`の手順に従って依存関係をインストールしてください。」
4. ポート8000が使用中かどうかを `netstat -ano | findstr ":8000.*LISTENING"` で確認する。
   - 使用中でかつ既存プロセスが本ダッシュボードのuvicornである可能性が高い場合（ポート競合の大半は
     「前回の起動が残っている」ケース）は、**新規起動をスキップし**ブラウザを開く処理に進む
     （AC4.3の「ポート使用」時のエラー処理を、単なるエラー表示で終わらせず「既に起動済みとみなして
     ブラウザだけ開く」という復旧動作にする。これにより二重起動やポート競合エラーで
     ユーザーを困らせない）。
   - 万一起動処理自体が失敗した場合は日本語エラーダイアログを表示する。
5. uvicornを非表示ウィンドウで起動する:
   `start "" /min powershell -NoProfile -WindowStyle Hidden -Command "& '%VENV_PY%' -m uvicorn app:app --port 8000"`
   （`%~dp0`がカレントディレクトリなので`app:app`の解決に問題はない。README同様`--reload`は
   本番導線では付けない）。
6. サーバのヘルスチェックを行うポーリングループ（最大10秒、0.5秒間隔）で
   `http://127.0.0.1:8000/` にアクセスできるようになるまで待つ
   （`powershell -Command "try{iwr http://127.0.0.1:8000/ -UseBasicParsing -TimeoutSec 1}catch{exit 1}"`
   の戻り値をループで確認）。10秒経っても応答が無ければエラーダイアログを表示して終了する。
7. 起動確認後、既定のブラウザで開く: `start "" "http://127.0.0.1:8000/"`。
8. 正常終了時は自身は特にpauseせず終了する（サーバプロセスはバックグラウンドで動き続ける設計。
   終了させたい場合はタスクマネージャーからの手動終了、または将来的に「サーバ停止.bat」を別途用意）。

### 7.2 `launch_dashboard.vbs` の仕様

ユーザーがダブルクリックする実体。内容は次の1行のロジックに要約される（擬似コード）:

```
scriptDir = 自分自身のあるフォルダ
CreateObject("WScript.Shell").Run """" & scriptDir & "launch_dashboard.bat""", 0, False
```
第2引数 `0` = ウィンドウ非表示、第3引数 `False` = 完了を待たない（bat側は自走してブラウザを開く
ところまで面倒を見る）。これにより **ユーザーの体験としてはダブルクリック→数秒後にブラウザが開く
だけ**で、コンソール画面は一切見えない。

### 7.3 起動失敗時の日本語エラー表示（AC4.3）

`.bat`は非表示実行されるため`echo`やコンソール出力はユーザーに見えない。よって失敗時は必ず
**メッセージボックス**で通知する。追加の依存関係（PyInstaller等）を増やさずWindows標準機能のみで
実現するため、`mshta`（Windows標準搭載のHTMLアプリケーションホスト）を使ったワンライナーを
エラー分岐ごとに呼び出す:

```
mshta vbscript:Execute("MsgBox ""仮想環境(.venv)が見つかりません。README.mdの手順に従ってセットアップしてください。"", 48, ""ABM Dashboard 起動エラー"":close")
```

エラーケースごとに文言を出し分ける（.venv未検出／uvicornがヘルスチェックに応答しない／その他の
起動失敗）。README（AC4.4）には「.venvの想定位置＝リポジトリ直下」「.venvが標準位置に無い場合は
`launch_dashboard.bat`内の`VENV_PY`変数を編集する」旨を明記する設計とする。
