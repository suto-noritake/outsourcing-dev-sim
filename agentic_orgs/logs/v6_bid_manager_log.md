# v6 Bid Manager Log

私はBid Managerとして、既存資産と今回の確定方針を突き合わせたうえで、このv6は**条件付きでGo**と判断した。理由は、要求そのものは既存リポジトリの文脈（ABM資産 + マルチエージェント運用知見）と強く接続しており、実現価値も高い一方で、実行の成否が **GitHub Copilot CLIの実機仕様確認** に強く依存するためである。特に「実クレジットを消費する独立サブプロセス実行」「Markdown定義チーム」「メンバー間コンテキスト分離」は、要件としては明快だが、CLI引数・セッション分離・ログ取得方式を推測で固定すると後工程で破綻しうる。

## 私が読んだ既存資産の要点

### 1. `docs/multi_agent_dev_playbook.md`

私の理解では、このリポジトリで確立済みなのは「Bid Manager → Architect → Implementer → QA」を中心とする4ロール制パイプラインである。重要なのは次の点だった。

- Bid Managerは要求整理・AC化・リスク指摘が主務であり、**事実確認が必要な内容は後工程で必ず再検証される前提**になっている。
- Architectは前工程を鵜呑みにせず、**既存コードや実資産と突き合わせて確定仕様を作る責務**を負う。
- モデル選定指針として、Bid Managerは軽量、Architectは最上位、QAはクロスベンダーが推奨されている。
- 既知の落とし穴として、軽量モデルの事実誤認、出力ファイル未生成、プロセス後始末漏れが明記されている。

今回のv6でも、このプレイブックはそのまま再利用できる。ただし、従来は「人間 + 上位AIが各sub-agentを都度発注」していたのに対し、今回はその社内パイプライン自体をCopilot SDK/CLIベースでプロダクト化する点が新しい。

### 2. `outsourcing_sim/params.py` と関連ABM文脈

私は `SimParams` を確認し、少なくとも以下を委託元ペルソナ化の入力候補として把握した。

- `gamma`: クライアント側の難易度エスカレーション率。実質的に「強欲さ/野心度」。
- `budget_c0`, `budget_c1`: クライアントの予算提示ルールの係数。
- `difficulty_0`: 初期要求難易度。
- `funds_0`: 受託会社の初期資金体力。
- `alpha`: エージェント数増加の収穫逓減。大人数投入への効き方。
- `k1`: 全体コスト水準のスケール。
- `partial_pay`, `r_min`, `max_consecutive_failures`: クライアントの支払寛容度・契約継続寛容度に関わる。

加えて `docs/DESIGN.md` / `docs/experiment_design.md` / `docs/report.md` から、A社（委託元）の「強欲さ」がB社（受託会社）の生存を強く左右するという整理は、今回の「ABMパラメータ→委託元ペルソナ変換」の根拠として流用しやすいと判断した。

### 3. `product/abm-dashboard/logs/model_manifest.md`

ここから私は、既存運用では

- Bid Manager: `gpt-5-mini`
- Architect: `claude-sonnet-5`
- Implementer: `gpt-5.3-codex`
- QA: `gemini-3.1-pro-preview`

のように、**役割ごとにモデルと推論強度を分ける設計実績**があることを確認した。したがって、今回のMarkdown frontmatterに `model` や `reasoning_effort` を持たせる要求は、既存資産と整合的である。

## Go / No-Go 判断

私は **Go（ただしArchitectによるCLI実機確認を着手条件とする）** と判断する。

### Goの理由

1. 既存ABMが委託元/受託会社の関係を既に抽象化しており、委託元ペルソナ生成の根拠がある。
2. 既存プレイブックが社内役割分担・ログ運用・モデル割当の土台を持っている。
3. 今回の要望は「フル自動」ではなく「半自動1サイクルずつ」なので、段階的に成立させやすい。

### 条件付きにした理由

1. `copilot` バイナリの実際の引数仕様・非対話実行可否・ログ取得法を私は未確認。
2. 独立サブプロセス実行が、現在の親セッションとどの程度干渉しないかは未確認。
3. 実クレジット消費・認証状態・失敗時の再実行コストが無視できない。

## Acceptance Criteria

### AC群A: 全体アーキテクチャ

- AC-A1: ルート配下に `agentic_orgs/` を新設し、その直下に `client_company/` と `contractor_company/` を持つ。
- AC-A2: 両社の配下に少なくとも `team/` と `templates/` または同等の設定/プロンプト格納領域を持ち、**メンバー定義と実行時成果物を分離**する。
- AC-A3: 実行ログは `agentic_orgs/logs/` 配下に集約されるが、会社・案件・実行回・メンバー単位で識別可能な命名規則を持つ。
- AC-A4: 受託会社システムと委託元会社システムは、どちらも **GitHub Copilot CLIをサブプロセスとして呼び出す実行器** を持つ設計である。
- AC-A5: 本v6のスコープは**半自動の1サイクル実行**であり、ユーザーが各ステップで確認して次コマンドを叩けるUXを前提とする。無人Nサイクル連続運転を前提にしない。
- AC-A6: 受託会社システムは特定製品固定ではなく、**任意の要求書 + 任意の対象ワークスペース**を入力として扱える設計である。

### AC群B: Markdownチーム管理

私は frontmatter の最小必須項目を次のように整理する。

- `id`: メンバー識別子（一意）
- `name`: 表示名
- `enabled`: 有効/無効
- `role`: 役割名（例: bid-manager, architect, implementer, qa）
- `model`: 使用モデル名
- `reasoning_effort`: 推論強度
- `specialty`: 得意分野（文字列または配列）
- `order`: 実行順序
- `depends_on`: 依存先メンバーID配列
- `input_artifacts`: 期待入力の種類
- `output_artifacts`: 生成成果物の種類
- `timeout_sec`: 実行タイムアウト方針

本文は、そのメンバー固有の人格・判断ポリシー・禁止事項・レビュー観点を自然言語で記述する領域とする。

検証可能な受け入れ条件は以下。

- AC-B1: `team/*.md` を読み込むだけで有効メンバー一覧を構成できる。
- AC-B2: `enabled: false` のメンバーはファイルが存在しても実行対象にならない。
- AC-B3: 新メンバー追加は **Markdownファイル追加のみ**、停止は **`enabled: false` または削除のみ** で反映できる。
- AC-B4: `depends_on` に基づく実行順制御が可能で、循環依存は明示的エラーとして検出される。
- AC-B5: frontmatter欠落・型不整合・未知モデル名・重複`id`は、静かに無視せず設定エラーとして報告される。
- AC-B6: 同一roleの複数メンバー定義を許容する場合、その並列/逐次実行規則が設定から機械的に決まる。

### AC群C: コンテキスト分離

- AC-C1: 各メンバー実行は毎回**独立した `copilot` サブプロセス**として起動される。
- AC-C2: あるメンバーのプロンプトには、前メンバーの会話履歴そのものは渡さず、**明示的な成果物ファイルの内容のみ**を入力とする。
- AC-C3: ログ/成果物パスは少なくとも `company`, `project_or_case`, `run_id`, `member_id` を識別できる。
- AC-C4: 同一案件でBid Manager→Architectと流しても、Architect側が前プロセスの内部会話状態を自動継承しないことを、実行方式またはCLI仕様で説明できる。
- AC-C5: メンバー失敗時も、失敗ログは当該メンバー単位で残り、他メンバーのログを汚染しない。
- AC-C6: 「コンテキスト共有禁止」の例外は**ファイル成果物のみ**であり、そのI/O境界が実装上も明示される。

### AC群D: 委託元会社システム

私は委託元会社システムの役割を「ABMパラメータを根拠に、要求書作成者/レビュー担当者を擬似的に演じること」と整理した。

#### D-1. ペルソナ変換ルールの下書き

- `gamma` 高: より野心的、短期で要求を高度化しやすい、レビューも厳しめ。
- `budget_c0`, `budget_c1` 高: 初期予算・難易度連動予算に余裕がある。要求の野心度を支えやすい。
- `partial_pay` 高: 失敗に寛容で、改善前提の関係維持に寄る。
- `r_min` 高 / `max_consecutive_failures` 低: 契約継続に厳格、レビューでの減点が大きい。
- `difficulty_0` 高: 初回から高難度の要求書を出しやすい。
- `funds_0` は本来B側資源だが、委託元視点では「相手の体力をどう見積もるか」の補助文脈として使う余地がある。ただし一次入力にするかはArchitect判断。

#### D-2. 要求書生成・納品審査のI/O案

- 入力候補:
  - ABMパラメータセット（JSON/YAML/CLI引数）
  - 対象プロダクトの概要
  - 今回の依頼テーマ
  - 直前サイクルの納品物（任意）
- 出力候補:
  - `request_brief.md`（要求・制約・優先度・予算感覚・レビュー観点）
  - `acceptance_criteria.md`（委託元視点の検収条件）
  - `review_feedback.md`（納品に対する差戻し/承認コメント）

検証条件:

- AC-D1: 同じABMパラメータセットを与えたとき、委託元の要求トーンとレビュー厳しさの根拠を説明できる。
- AC-D2: 委託元の出力は、受託会社がそのまま入力として読める**ファイル成果物**である。
- AC-D3: レビュー結果は「承認 / 条件付き承認 / 差戻し」等の機械可読な最終判定を持つ。
- AC-D4: ペルソナ文と具体要求文が分離され、後工程が「性格設定」と「要求本文」を混同しない。

### AC群E: 受託会社システム

私は受託会社システムの役割を「要求書 + 対象ワークスペースを入力として、社内パイプラインを半自動で回す汎用受託実行基盤」と整理した。

#### E-1. 入出力形式案

- 入力:
  - `request_brief.md`
  - `acceptance_criteria.md`
  - 対象リポジトリ/ワークスペースのパス
  - 実行対象チーム定義ディレクトリ（既定は `contractor_company/team/`）
- 出力:
  - 各メンバーのログ
  - 中間成果物（要件整理、設計書、実装指示、QA判定）
  - 最終サマリ（今回どこまで進んだか、次に人間が叩くべきコマンドは何か）

#### E-2. プレイブックのMarkdown化下書き

既存 `docs/multi_agent_dev_playbook.md` のロール定義は、各メンバーMarkdown本文に次の形で分配できる。

- Bid Managerメンバー: 要求整理、Go/No-Go、AC化、リスク列挙
- Architectメンバー: 既存コード検証、前工程是正、具体設計確定
- Implementerメンバー: 実装 + 実機検証必須
- QAメンバー: AC項目別の独立再検証、必要なら修正、最終判定

検証条件:

- AC-E1: チーム構成を `team/*.md` の差し替えだけで変更しても、同じ要求書入力から別編成パイプラインを起動できる。
- AC-E2: 既存プレイブックの責務分離がMarkdown本文に落ち、コード側に役割知識をハードコードしない。
- AC-E3: 実行順は `order` / `depends_on` から決定され、人間が「今回はArchitectまで」などで停止できる。
- AC-E4: 対象ワークスペースは任意パスを受けられ、`product/abm-dashboard/` 固定実装にならない。

## リスク・懸念点

1. **`copilot` 実機仕様未確認**  
   私はCLIの実オプションを検証していない。`--help` で確認せずに設計すると、想定していた非対話実行・モデル指定・出力制御・認証継承が存在しない可能性がある。

2. **実クレジット消費コスト**  
   今回はモック不可であり、サイクルを回すたびに本当に課金/クレジット消費が発生する。再試行戦略・ログ粒度・無駄打ち抑制が必須。

3. **親セッションとの干渉可能性**  
   サブプロセス起動した `copilot` が現在進行中セッションとセッション共有/ロック競合/認証共有問題を起こさない保証がまだない。

4. **YAML frontmatterパース失敗**  
   些細な書式崩れでチームが壊れる恐れがある。エラー表示、必須項目検証、unknown field許容方針が必要。

5. **循環依存・停止不能パイプライン**  
   `depends_on` を導入する以上、DAG検証とエラーメッセージが必要。

6. **モデル名・reasoning_effortの妥当性**  
   frontmatterに書けても、CLI側がそのモデル/推論強度を受理するとは限らない。定義値と実機仕様の照合が必要。

7. **ログと成果物の肥大化**  
   半自動であっても案件ごと・メンバーごとにログを残すと、長期運用でノイズや容量問題が出る。保存期間・命名規則が必要。

8. **ファイル経由伝達の情報欠落**  
   コンテキスト分離を守るほど、暗黙知が伝わらず後工程の判断材料が痩せる。成果物テンプレートを相当に丁寧に設計しないと品質低下が起こる。

9. **Windowsパス・文字コード・日本語プロンプト**  
   このリポジトリ運用ではWindowsパスと日本語本文が前提になりそうであり、サブプロセス引数引用やUTF-8/BOMの扱いを誤ると壊れやすい。

10. **汎用受託化の抽象度不足**  
   `abm-dashboard` 由来のロール設計をそのまま一般化すると、汎用新規製品に不要な前提が混入する恐れがある。

## 私の判断メモ

- 私は「委託元会社システム」と「受託会社システム」を同時に作る要求を、1つの巨大自動化ではなく、**2つの組織ランナー + ファイルI/O契約**として分解するのが安全だと見ている。
- 私はチーム定義をMarkdown化する方針に賛成である。既存のモデルマニフェスト/プレイブックとの整合性が高く、非エンジニアでも編成変更しやすい。
- 一方で、**Markdownに何でも背負わせすぎると設定言語化して破綻する**ので、frontmatterは宣言、本文は自然言語、実行器は厳格バリデーション、という分担がよい。
- 委託元ペルソナについては、今回は「ルール概要の下書き」までで十分であり、数式レベルの正規化やしきい値設計はArchitectがABM根拠を見て確定すべきだと判断する。

## 次工程への申し送り

1. **最優先で `copilot --help` 等を実機実行し、CLIの実オプション・非対話実行方法・モデル指定・出力取得・セッション分離の可否を確認してほしい。** 私はそこを未検証のまま仮定で確定していない。ここがv6の最大不確実性である。  
2. `agentic_orgs/` 配下の最小ファイル/ディレクトリ構成、ログ命名規則、run_id設計をArchitectで確定してほしい。  
3. `team/*.md` frontmatterの**厳密スキーマ**（必須/任意/型/デフォルト/未知項目方針）をArchitectで固定してほしい。  
4. `depends_on` の循環検出、`enabled` の意味、同一role複数定義時の実行規則をArchitectで明文化してほしい。  
5. 委託元ペルソナ変換は、`gamma`, `budget_c0/c1`, `difficulty_0`, `partial_pay`, `r_min`, `max_consecutive_failures` を中心に下書きしたが、どのパラメータを一次根拠に採用するかはArchitectで最終決定してほしい。  
6. 汎用受託システムとして、対象ワークスペースの受け渡し方法、成果物テンプレート、途中停止/再開UXを設計してほしい。
