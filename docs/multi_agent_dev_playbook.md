# マルチエージェント開発プレイバック — 4ロール制の製品開発プロセス

このドキュメントは、`outsourcing-dev-sim`リポジトリのPhase6（ABMインタラクティブ
ダッシュボードのv1新規開発・v2クライアントフィードバック対応）で実践した
「異なるLLMモデルを役割別sub-agentとして動かす製品開発プロセス」を、**別の製品・別の
プロジェクトでも再利用できる形に一般化したガイド**である。

具体的な実施記録・発見された知見は
[`docs/experiments/005_phase6_product_multiagent_case_study.md`](experiments/005_phase6_product_multiagent_case_study.md)
を参照。本ドキュメントは「次に同じことをやる時に何をすればよいか」の手順書である。

---

## 1. いつ使うプロセスか

- 実装対象がある程度明確な（既存コードベースの拡張、新規小〜中規模プロダクト、
  既存製品への機能追加/バグ修正）タスクで、
- 「発注者（オーケストレーター＝人間 or 上位AI）」と「実行者（複数のsub-agent）」を
  分離することで、単一のLLMに全工程を任せるより検証の目が増え、品質が上がると
  期待できる場合に適用する。
- 単純な1〜2ファイルの軽微な修正には過剰。**複数の設計判断・複数ファイルにまたがる
  実装・受け入れ基準の検証が必要な規模**が目安。

## 2. 役割定義

| 役割 | 責務 | 出力形式 |
|---|---|---|
| **Bid Manager**（受託可否判断） | 要求を読み、実現可能性を評価しGo/No-Go判断。Acceptance Criteria（受け入れ基準）をチェックリスト形式で作成。リスク・不明点を指摘。 | `logs/bid_manager_log.md`（一人称、判断根拠つき） |
| **Architect**（設計） | Bid Managerの成果物を**鵜呑みにせず**、実際のソースコード・既存資産と突き合わせて検証・訂正した上で、具体的な設計（API契約、ファイル構成、データ形式、UI方針、ガードレール）を確定する。 | `logs/architect_log.md`（確定仕様。次工程がそのまま実装できる具体性） |
| **Implementer**（実装） | Architectの仕様通りに実装する。**実際にコードを動かして**（テスト実行、サーバー起動＋実リクエスト等）検証してから完了報告する。仕様からの逸脱があれば理由を明記。 | `logs/implementer_log.md` + 実コード |
| **QA**（検証） | 前工程の成果物を**独立した視点で**再検証する。Acceptance Criteriaを1項目ずつ実際に確認し、可能ならコードレビューで追加のバグを探す。発見したバグはその場で修正してよい。 | `logs/qa_log.md`（最後に明確な「## 最終判定」＝Pass/Fail） |
| **オーケストレーター** | 各ロールへの発注・引き継ぎ・最終統合。**サブエージェントの自己申告を信用せず、自分でも独立して再検証する**（後述チェックリスト）。ユーザーへの最終報告・コミット/プッシュ。 | 本人（人間 or 上位AI）が担当 |

### 2.1 専門ロールの追加（基本4ロール以外が必要になった場合）

基本4ロールは「要求整理→技術検証→実装→独立検証」という汎用的な流れだが、要望の性質が
**評価基準の異なる複数の専門性**（例: 統計的・工学的な妥当性検証 と、ビジュアルデザインの
一貫性判断）にまたがる場合、無理に1ロール（多くはArchitect）に両方を背負わせず、
**専任の追加ロールを新設する**ことを検討する（実例: Phase6 v5の「Brand Designer」）。

- 追加ロールは、Bid Manager完了後にArchitectと**並行実行**できる設計にすると、
  待ち時間を増やさずに専門性を分離できる（両者に依存関係がない場合）。
- 追加ロールへの発注時は、**裁量を与える範囲と、変更してはいけない不変条件を明確に分離して
  指示する**こと（例: 「配色・タイポグラフィは白紙から刷新してよいが、既存の情報構造・
  機能配置は変更しない」）。これを曖昧にすると、専任の創造的権限を持つロールが、
  機能や使い勝手を犠牲にしてでも自分の専門領域の理想を優先する結果になりかねない。
- Implementerは、複数の専門ロールから出た確定仕様を**統合するだけ**で済むようにする
  （専門ロール側で「Implementerがそのまま実装できる粒度」まで仕様を具体化させておく）。

## 3. モデル・reasoning_effort 割当の指針

Phase6で採用した実例（`gpt-5-mini`/`claude-sonnet-5`/`gpt-5.3-codex`/`gemini-3.1-pro-preview`）
は一例であり、使えるモデル一覧はプロジェクトごとに異なる。以下の**選定基準**を優先する:

- **Bid Manager**: 定型的な要求整理・チェックリスト作成が中心なので、コスト効率重視で
  軽量モデル・低reasoning_effortでよい。**ただし「事実確認を要する内容」（既存コードの
  挙動、パラメータの意味等）を書かせる場合は、その内容を必ず後工程（Architect）で
  ソースコードと突き合わせて検証させること。** これを怠ると誤情報がそのまま
  最終成果物に混入するリスクがある（Phase6 v2で実際に発生した事例あり）。
- **Architect**: 設計判断の質が全工程に波及するため、最も高性能・高reasoning_effortの
  モデルを割り当てる。既存資産（ソースコード、既存の設計ドキュメント）を必ず読み込ませ、
  前工程の成果物の妥当性を検証させる。
- **Implementer**: コード生成に強いモデルを使い、reasoning_effortは高めに設定する。
  「書いて終わり」ではなく「実際に動かして確認する」ことを明示的に指示する。
- **QA**: **Architect/Implementerとは異なるベンダー・異なる系統のモデルを意図的に選ぶ**
  （クロスベンダーレビュー）。同一モデル・同一視点による見落としのリスクを下げる狙い。
  Phase6では実際にこの設計判断がバグ発見につながった実績がある。

## 4. 発注プロンプトのテンプレート

各役割への`task`ツール呼び出し（`agent_type="general-purpose"`, `mode="sync"`推奨、
必要なら`model`/`reasoning_effort`を明示指定）には、以下の要素を必ず含める:

1. **役割の自己認識**: 「あなたは〇〇（役割名・日本語名）です」と明示し、
   「自分の一人称視点で、判断根拠とともにログに記録してください」と指示する。
2. **読むべき入力ファイルの具体的パス**: 前工程のログファイル、関連する既存ソース
   コードのパスを列挙する（曖昧な「関連ファイルを読んで」ではなく、実在するパスを渡す）。
3. **書くべき出力ファイルの具体的パス**: `logs/xxx_log.md`のように、次工程が迷わず
   読める場所を指定する。
4. **具体的な検証・実行指示**（Implementer/QAの場合）: 「実際にテストを実行しろ」
   「実際にサーバーを起動してHTTPリクエストを送れ」「起動したプロセスは必ず停止しろ」
   など、"やったふり"を防ぐための具体的な手順を明示する。
5. **締めの「## 次工程への申し送り」セクション**: 次のロールが何を確認すべきか、
   自分が検証しきれなかった項目（例: GUI操作、他OSでの挙動）を明記させる。

## 5. SQL todosでの進行管理パターン

役割ごとに1つのtodoを作り、直列の依存関係（`todo_deps`）でパイプラインを表現する:

```sql
INSERT INTO todos (id, title, description) VALUES
  ('xxx-bidmanager', 'Bid Managerロールで要求を精緻化', '...'),
  ('xxx-architect', 'Architectロールで設計確定', '...'),
  ('xxx-implement', 'Implementerロールで実装', '...'),
  ('xxx-qa', 'QAロールで検証', '...'),
  ('xxx-integrate-verify', 'オーケストレーターが統合・独立検証', '...'),
  ('xxx-docs-commit', 'ドキュメント整備・コミット・プッシュ', '...');

INSERT INTO todo_deps (todo_id, depends_on) VALUES
  ('xxx-architect', 'xxx-bidmanager'),
  ('xxx-implement', 'xxx-architect'),
  ('xxx-qa', 'xxx-implement'),
  ('xxx-integrate-verify', 'xxx-qa'),
  ('xxx-docs-commit', 'xxx-integrate-verify');
```

各ロールの呼び出し前に`status='in_progress'`に更新し、成果物を自分で確認してから
`status='done'`に更新する（サブエージェントの完了報告だけで`done`にしない）。

## 6. オーケストレーターの独立検証チェックリスト（必須）

サブエージェントの「やりました」報告は**必ず**以下の方法で裏を取ってから次工程へ進める:

- [ ] **成果物ファイルが実在するか** `glob`/`view`で確認する（ツール呼び出しの中断で
      ファイルが生成されないまま完了扱いになるケースが実際にある → 単純リトライで解決）
- [ ] **テストは自分でも再実行する**（サブエージェントの「7件パスしました」を鵜呑みに
      せず、同じコマンドを自分の手元でも走らせて確認する）
- [ ] **サーバー/プロセスを実際に起動してAPIを叩く**（コードレビューだけで
      「動くはず」と判断しない）
- [ ] **起動したプロセスが本当に停止しているか確認する**（`netstat`/`Get-Process`等で
      残存プロセスがないか確認する。サブエージェントが「停止済み」と自己申告しても
      実際には残っていることがある）
- [ ] **前工程の成果物に事実誤認がないか、疑わしい箇所は自分でソースを読んで確認する**
      （特に軽量モデルが書いた「説明文」「パラメータの意味」等）

## 7. 既知の落とし穴と対処

| 落とし穴 | 対処 |
|---|---|
| sub-agent呼び出しがツール実行エラーで中断し、出力ファイルが生成されない | `glob`で成果物の不在を確認し、同一指示で単純リトライする |
| 軽量モデル（低reasoning_effort）が書いた「事実確認を要する内容」に誤りが混入する | 必ず後工程（Architect等の高ティア）でソースコードと突き合わせて検証・訂正する工程を挟む |
| サブエージェントが「完了・検証済み」と報告しても、実際にはプロセスが残存している等の後始末漏れがある | オーケストレーターが独立して`netstat`等で確認する |
| 複数ロールが同じ設計判断について異なる前提を置く（例: フィールド名の推測違い） | Architectの工程で必ずソースコードの実名・実挙動と突き合わせて確定させ、以降のロールはArchitectの確定版を正とする |

## 8. クライアントフィードバック対応（vNイテレーション）パターン

製品を一度出荷した後にユーザー/クライアントから実際のフィードバックが来た場合も、
**同じ4ロールパイプラインをそのまま再利用できる**:

1. 生のフィードバック（クレーム、要望）をそのままBid Managerに渡し、
   優先順位付き Acceptance Criteria（AC1, AC2, ...）に整理させる。
2. Architectに、Bid Managerの整理結果を**実装済みコードと突き合わせて検証**させ、
   具体的な修正方針（何をどう直すか、なぜその方式を選ぶか）を確定させる。
3. Implementer→QAは通常の新規開発と同じ手順。
4. 既存のAPI/データ契約を壊さないことが多くの場合重要な制約になる
   （既存テスト・既存利用者との後方互換性）。Architectの設計時に明示的に
   「何を変えてよく、何を変えてはいけないか」の線引きをさせること。
